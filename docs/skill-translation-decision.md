# Skill 翻译决策说明

- **日期**：2026-08-18
- **状态**：决定不翻译，保留英文原版
- **范围**：my-superpowers 插件下 11 个 skill 的 `SKILL.md`（含 `description` 字段与正文）

## 背景

平时主要使用国内模型（GLM、Qwen、DeepSeek 等），一度考虑将 superpowers 的 skill 文档翻译成中文，动机有二：

1. 担心英文 description 在中文输入场景下触发不准
2. 想通过中文化省 token

经实际使用与讨论后，确认触发无问题，省 token 收益边际，最终决定**不翻译**。本文记录决策依据，供日后复查。

## Skill 文本的两类构成

每个 `SKILL.md` 由两部分组成，作用与消耗模式完全不同，需分别评估：

| 部分 | 作用 | 消耗频率 |
|---|---|---|
| `description`（frontmatter 字段） | 被注入系统提示词，供模型判断何时触发该 skill | 每轮对话常驻 |
| 正文 Markdown | skill 被调用后才加载，指导模型如何执行 | 仅触发时加载 |

## 触发原理澄清

### 基本机制

1. 所有 skill 的 `description` 打包进系统提示词，每轮常驻
2. 每轮模型看到的输入为：`系统提示词(含所有 description) + 完整历史对话 + 当前用户消息`
3. 模型基于语义匹配判断是否调用 `use_skill`，匹配的是**意图语义**而非字面语言

### 关于"模型输出是否参与触发"

参与，且是常态而非例外。多轮对话下，历史对话里包含模型此前每一轮的输出，这部分每轮都进入下一轮的触发判断输入。因此"模型之前的输出"是触发判断的常规输入之一。

但这不意味着 description 必须与模型输出语言一致——触发是语义层面匹配，模型具备跨语言语义理解能力。英文输出上下文与中文 description 之间，模型能完成语义对齐，转换成本极低。

## 翻译收益与成本分析

### 收益

- **省 token**：主要来自 `description`（常驻部分）。但 11 个 description 总量有限，占系统提示词比例小，相对工具定义、规则段等大块，省下的量级边际。正文仅在触发时加载，翻译收益可忽略。
- **触发命中率**：实测无问题，不构成翻译理由。

### 成本

- **维护负担**：原版 superpowers 持续更新，叠加翻译层后 upstream 同步成本翻倍。本仓库已是精简适配版，不宜再背翻译债。
- **强约束语气弱化风险**：正文大量使用 `MUST` / `Do NOT` / `HARD-GATE` / `Anti-Pattern` 等英文硬约束词，翻译后语义覆盖面与语气强度未必对齐，可能弱化模型对约束的遵循。
- **格式破坏风险**：dot 流程图、代码示例、文件路径、skill 名（作为调用 ID）均不可翻译，混排易出错。
- **会贬值的投资**：国内模型英文指令遵循能力持续提升，翻译的相对价值随时间下降。

## 决策

**不翻译，保留英文原版。**

核心理由：

1. 触发已验证正常，翻译不解决实际问题
2. 省 token 收益边际，不值得引入维护成本
3. 强约束语气的弱化风险无法量化但确实存在
4. 英文原版对 upstream 同步零额外成本

## 重新评估的触发条件

若未来出现以下信号，可重新考虑是否翻译（优先评估 `description` 字段）：

- 实测发现中文输入场景下 skill 触发率明显下降
- 国内模型 tokenizer 在中文 token 效率上有显著优势，且 description 占系统提示词比例因其他改动上升
- 原版 superpowers 进入维护停滞，upstream 同步不再是负担

重新评估时仍建议**只动 description，不动正文**，并按"什么场景该触发"重写中文语义，而非直译。
